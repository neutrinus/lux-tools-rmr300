# U16 Firmware Analysis — GD32F303CGT6 (Board MCU)

## Overview

U16 (GD32F303CGT6, ARM Cortex-M4 @ 72 MHz) is the **border-wire and lift sensor MCU** on the mainboard. It digitises the two boundary-wire coils, classifies the signal, reads the two lift sensors and reports the result to U13 as JSON. It has no connection to the display board and no motor, motor-driver or power code: buttons and the display UART go to the ESP32 and U13 (evidence: [`20261009_claude_investigation.md`](../../20261009_claude_investigation.md)).

The image is byte-identical to the U16 dump of the MI 302 analysed in [salonnikov/mower-stock-reverse](https://github.com/salonnikov/mower-stock-reverse) (`reverse-v2/chip2/`, their "chip2"), so their addresses apply here unchanged.

**420 functions** identified via Ghidra decompilation.

## Main Task: `comm_task` (FUN_08013680)

The main FreeRTOS task loop:

```
comm_task()
  loop:
    wait on queue (semaphore, INF timeout)
    if signal_flag:
      handle signal state machine
    
    if first_run:
      init factory driver with retry  (FUN_08017884)  // startup calibration
    else:
      run board process  (FUN_08014ac8)               // coil status cycle
    
    deal_lift_sensor  (FUN_08013970)                  // lift sensor state machine
    dispatch_messages  (FUN_08019914)                  // send JSON messages
    
    delay 35 ticks (watchdog kick)
```

## Communication Protocol

### Physical Layer: UART (mport driver)

File: `driver_mboard_port_snk_v2.c`
Driver tag: `"mport drv"`

**Transmission (`send_string_dpport_snk_v2`, FUN_08019a18):**
```
send_string(data, length, param3, param4):
  if length >= 129:  // max 128 bytes
    log ERROR "send string length=%d too long"
    return error
  if length == 0:
    log WARN "@send len=0"
    return error

  // Wait for TX ready (semaphore with timeout)
  try 50000 iterations:  // ~busy-wait loop
    if semaphore_available:
      break
  if timeout:
    log ERROR "@wait send string overtime"
    return error

  // Send
  take_semaphore()
  clear_buffer(0x80)         // 128-byte buffer
  copy_data(data, length)
  set_length(length)
  enable_transmit()
  return success
```

**Reception:** Handled by `port_receive_callback` (callback registered during init).

### Data Format: JSON via cJSON

Messages are serialized using **cJSON** library. Key cJSON functions identified:
- `cJSON_Parse` / `cJSON_Print` (used at 0x08012fd4)
- `cJSON_AddItemToObject` (FUN_08012d78)
- `cJSON_AddItemToArray`
- `cJSON_GetObjectItem`
- `cJSON_CreateObject`, `cJSON_CreateNumber`, `cJSON_CreateString`

### Message Types

U16 sends these JSON messages to U13:

| Message | Trigger | Contents |
|---------|---------|----------|
| **border_message** | Flag at struct+0x12 == 0 | Border sensor data (left/right coil readings) |
| **version_message** | Flag at struct+0x14 == 0 | Hardware/software version |
| **seach_border_message** | Flag at struct+0x18 == 0 | Search border mode status (note: typo "seach" in original) |
| **follow_border_message** | Flag at struct+0x19 == 0 | Follow border mode status |

The message dispatcher (FUN_08019914) reads these flags from the board sensor data structure and builds JSON using cJSON operations.

### Incoming Commands

U13 sends JSON commands to U16. The JSON parser (`get_process_comm`, FUN_080180a0 / FUN_08017f92) handles:
- Objects `{}` — recursive key-value parsing
- Arrays `[]` — recursive element parsing
- Strings `""` — with escape sequence support (\\, \", \n, \r, \t, \f, \b, \uXXXX)
- Numbers — integer, float with sign, decimal point, exponent
- Booleans — `true` / `false` (memcmp)
- Null — `null` literal

Parser returns typed tokens:
| Type code | Meaning |
|-----------|---------|
| 0x2 | boolean (true) |
| 0x4 | null |
| 0x8 | number (double) |
| 0x10 | string |
| 0x20 | array |
| 0x40 | object |

Error handling: "error cmd =%d", "message point is null", "get message cmd is null", "get message string is null"

## Sensors

### Lift Sensors (deal_lift_sensor, FUN_08013970)

Two hall-effect sensors detect when the mower is lifted.

State machine (state stored at struct offset 0x0e):

| State | Meaning | Detection |
|-------|---------|-----------|
| 0 | `lift none` | Neither sensor triggered |
| 1 | `both lifted` | Both sensors triggered |
| 2 | `left lifted` | Left sensor triggered |
| 3 | `right lifted` | Right sensor triggered |

Debounce: 10 consecutive samples required to confirm state change.
Counter variables at struct offsets 0x0f-0x11 track sample counts for each state.

### Border Wire Sensors (bdsensor)

File: `driver_board_sensor/driver_bdsensor.c`
Two coils under the chassis sense the electromagnetic field from the boundary wire.

Acquisition (`bdsensor_init` `FUN_08019d34`, pin and ADC setup `FUN_08019bf4`):
- Dual ADC with DMA: `DAT_08019cf0` = `0x40012400` (ADC0), `DAT_08019cf4` = `0x40012800` (ADC1). Coils on ADC0 channel 5 and ADC1 channel 9, sample time 7 (`FUN_08012a04`). Which coil is left and which is right comes from the wiring and the order in `send_border_message`.
- Sample windows of 800 (fine) or 235 (coarse) samples (`+0x92`), period constant 18868 (`+0x78`).
- **Base voltage** (`FUN_08012b6c`, check `FUN_0801a1f8`): the receiver's DC offset, the average of several conversions. Valid range 1906–2191; outside it the firmware logs `"base voltage=%d error, set default 2048"` and uses 2048. It shifts the zero, it does not scale the signal, and it has nothing to do with the battery.

Detection (`FUN_08015fa8` → `FUN_0801baf8`):
- A sample counts when `|sample| > 2500`; in "strong signal" mode (latched after more than 20 saturated windows) the threshold is 5000.
- Fewer than 5 counted samples in a window = no wave; more than 600 = interference; otherwise a valid wave. Zero crossings (`FUN_08015dcc`) and the area/direction integrator (`FUN_08015260`) give `area` (0/1/2/3) and `str` per coil.
- U13 has no command that changes these thresholds; it sends only commands such as start search / follow border / reset and `{"cmd":32772,"rtc":…}`.
- Changing the sensitivity means patching the constants and redoing the flash CRC32 that the IEC 60730 self-test checks, or adjusting the coil front end in hardware.

### Status processing (FUN_08014ac8)

`FUN_08014ac8` reads the left and right coil status through the sensor vtable (`+8`, `+0xc`; 0 none, 1 in range, 2 over range, 3 over limit) and calls methods `+8` / `+0xc` of the "factory" driver object (`FUN_08019288`) in a counter-driven cycle (20 / 40 / 80). That object is not a motor driver: the U16 image has no SPI motor-driver, PWM-output or power code. What the two methods do is not identified [I: likely the start/stop of a collection or test cycle].
